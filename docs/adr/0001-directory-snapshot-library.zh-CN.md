# ADR 0001：目录化的本地快照库

- 状态：已采用
- 日期：2026-11-19
- 关联：#24（任务面板 Gitea 首屏与刷新）、#7（仓库作用域）

## 背景

本地快照库原来是一个缓存键一个 JSON 文件：每次刷新整份序列化、写临时文件再 rename；
`patchTicket` / `removeTicket` 也要重写整份。它没有库版本、没有行粒度、没有墓碑与变化日志，
因此刷新只能每次回一份完整列表，远端没变时也要付整份回传的代价。

面板需要三件存储层能力：

1. 客户端报出上次看到的库版本时，只回之后变化的行与墓碑；
2. 改一张票只写一张票；
3. 中途崩溃不产生半批可见数据。

同时明确不引入 SQLite 等原生/嵌入式数据库：打包与跨平台安装成本必须为零。

## 决策

一个缓存键一个目录。目录布局是适配器内部私事，调用方只认 `SnapshotStore` 接口：

```
<hash>.dir/
  meta.json              提交点：格式版本、库版本、仓库身份、远端版本、
                         票引用、墓碑、写入时算好的概览指标
  tickets/<hash>.json    每张票一个文件，只存后端原始数据
  changes.jsonl          追加式变化日志，每条提交记录变化的引用与墓碑
```

### 提交顺序即事务

一次写入固定为：

1. 写变化的票文件（临时文件 + rename）；
2. 追加变化日志；
3. 写 meta（临时文件 + rename）。

meta 是提交点。读路径先读 meta，再按 meta 里的票引用读票文件。崩溃只可能留下孤儿票文件、
未提交的日志尾巴或旧 meta，三者都不构成半批可见数据。下一次写入按 meta 版本截掉未提交的日志
尾巴，并清掉不再被引用的孤儿票文件。

### 两个版本号分开

- **远端版本号（source revision）**：后端给出的可比较标识与权威总数，回答「远端变了吗」。
  刷新把它作为 `ifRevision` 带回；一致时后端回 `notModified`，宿主回极小响应。
- **本地库版本（store revision）**：meta 里的单调递增提交序号，回答「本地库里有什么」。
  客户端带回上次看到的库版本，宿主用变化日志只回变化行与墓碑。

两者不能混用。远端版本读不到、总数漂移、增量被截断或父子能力与库里不一致时，宿主退回全量，
不交一份不可信的增量。

### 墓碑

删除不物理删行：meta 的 `tombstones` 记录「这一版里不存在」的票引用，变化集把它作为删除交出。
同一张票重新出现时，写入路径把墓碑清掉。墓碑只在变化日志的可读窗口内参与判定；日志轮转后
过旧的基线一律退回整份。

### 统计与原始数据

meta 保存写入时从同一份票数据算好的概览指标，读侧直接用，不再重算。写操作改票或删票时清空
指标，下一次刷新重新写回。库本身只存后端原始数据与这份统计，不存可接 / 阻塞 / 技能动作等判定结果；
判定规则升级不需要清库。

### 回退与自愈

- 日志轮转窗口外、客户端版本比库里新、票文件缺失或损坏：变化集读不出来，回整份。
- meta 或任一票文件损坏：该缓存键按没有缓存处理，不影响其它工作区。
- 格式版本不符：按没有缓存处理，不做迁移。
- 变化日志最多保留 512 条提交；更早的客户端基线回整份。

### 单写者

维持单写者假设：同一时刻只有一个宿主进程写本地快照库。当前不做文件锁；出现第二写者时再补。

## 后果

- 刷新回包从「整份列表」降为「变化行 + 墓碑」；远端没变时是极小的 not-modified 响应。
- 改一张票只写一个票文件；其它票文件不动。
- 目录里会短暂出现孤儿票文件；下一次写入清理，`prune` 会清掉读不出来的目录。
- 磁盘占用按票数增长；单工作区万级票量或出现第二写者时，再评估数据库方案。
- 变化日志的轮转窗口决定「最多能追多旧的客户端基线」；窗口外的请求付整份代价。
